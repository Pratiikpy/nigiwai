# Decisions

Every non-trivial decision: what, why, the alternatives and why they lost, and the evidence. Newest last. Evidence marked VERIFIED was checked against the real tool or API on the date shown.

## D1. Licence: MIT (2026-10-23)
- **Decision:** MIT.
- **Why:** Prateek's goal says "Use the MIT licence". The research folder's ARCHITECTURE.md section 11 recommended Apache-2.0 for its patent grant; that was a recommendation, the instruction is later and explicit.
- **Alternatives:** Apache-2.0 (patent grant, trademark carve-out), AGPL, BSL (not OSI, fails the launch requirement).
- **Consequence:** the Nigiwai name and brand assets are not licensed for reuse; NOTICE states that.

## D2. Auth: first-party sessions behind a provider interface (2026-10-23)
- **Decision:** the API owns signup, login, sessions and tenant roles (argon2id password hashes, server-side sessions in Postgres, `HttpOnly` `SameSite=Lax` cookie, CSRF token on mutating owner routes). An `IdentityProvider` interface lets a hosted provider replace it.
- **Why:** ARCHITECTURE.md chose Clerk, which needs an account, and the goal forbids creating accounts without approval. A product that cannot run from a clean checkout fails "judge mode works cold".
- **Alternatives:** Clerk (account), Auth.js (adds a second runtime and a user table we would still own), passkeys only (poor recovery story for a first release).
- **Risk:** more security code to own. Mitigated by tests for session fixation, CSRF, brute-force limits and cross-tenant access.

## D3. Bot protection on the public survey: first-party (2026-10-23)
- **Decision:** single-use signed nonce, honeypot field, minimum completion time, per-point burst detection and sliding-window rate limits. Cloudflare Turnstile is an optional adapter that switches on when a site key is configured.
- **Why:** Turnstile needs an account. The architecture already treated Turnstile as one layer of several.
- **Alternatives:** hCaptcha and reCAPTCHA (accounts, third-party scripts on a no-tracker page), proof-of-work CAPTCHA (hurts a 20 s phone survey).

## D4. Hosting: portable containers, no vendor lock-in (2026-10-23)
- **Decision:** the deliverables are container images (`api`, `worker`, `web`), a production Compose file, and infrastructure code for Cloud Run (OpenTofu). Postgres and Redis are plain connection strings, so Neon and Upstash work and so does any self-hosted pair.
- **Why:** no accounts may be created; the product must still be deployable the moment approval arrives.
- **Not verified:** the OpenTofu module cannot be applied without a cloud account. It is reviewed and linted, never applied (status NOT VERIFIED in BUILD_STATE).

## D5. Qloo transport policy (2026-10-23)
Evidence, all VERIFIED on 2026-10-23 against `@qloo/qloo-harness` 0.1.26 and the hackathon host:
1. `qloo api <command>` routes to the legacy endpoint CLI (`search`, `insights`, `entity`, `analyze`, `tags`). It prints entities already unwrapped. `--params '<json>'` merges arbitrary API parameters.
2. For a person-seed combination, REST returns `warnings: [{"type":"not_found", ...}]`; the CLI output has no warnings field (stderr empty). The CLI exposes no response headers either.
3. REST headers on the hackathon host now read `X-Second-RateLimit-Limit: 10` and `X-Month-RateLimit-Limit: 50000` (the research docs recorded 5 and 10,000).
4. `qloo api mcp` is a persistent stdio MCP server, but its `qloo_insights` tool only accepts `type, signal_entities, signal_tags, signal_location, filter_location, take, fields`. It cannot send `filter.tags`, `filter.results.entities`, `filter.popularity.max` or a radius, all of which the product needs.
5. Each CLI call starts a Node process (about 0.5 to 1.5 s overhead per call).
6. `entity` takes one id and has no `--params`; `tags` has no `--params`; `insights --filter-location` maps to `filter.location.query` (the wrong-area trap), so exact points go through `--params {"filter.location": "POINT(lon lat)"}`.
7. On Windows the npm `.cmd` shim breaks JSON arguments (cmd.exe quoting), so the harness is started as `node <package>/dist/bin.js` directly (`resolve_harness_command`).
8. Live parity tests (13, run 2026-10-23) pass: the same `/search` and place `insights` requests return the same entity ids through the harness and through REST.
- **Decision:** the Guard has two transports behind one interface. `HarnessTransport` (the `qloo api` CLI with `--params`) is the **primary** transport, as Prateek instructed, for every call whose result does not depend on `warnings` or headers: all `/search`, `/entities`, `/v2/tags`, `/v2/analysis/compare`, and `insights` without entity seeds. `RestTransport` is used (a) automatically as the fallback when the harness fails or times out, and (b) for `insights` calls that carry entity seeds, because only REST reports dropped seeds (trap 12) and the rate-limit headers the quota ledger needs. A parity test records that both transports return the same entity ids for the same request.
- **Verified live:** insights entities carry `type: "urn:entity"` and the real type in `subtype`, while `/search` and `/entities` use `types[]`; the first synthetic fixtures had this wrong and the live tests caught it. **Why not harness-only:** it would silently lose the dropped-seed warning, which the Guard uses to suppress explainability. **Why not REST-only:** the instruction names the harness, and the kit lists it as the supported event surface.
- **Open for Prateek:** see HUMAN.md H3 (whether to flip the default to REST).

## D7. Front-end styling: port the design system, not Tailwind (2026-10-23)
- **Decision:** the web app reuses the tokens, components and label system from the research folder's `design/` prototypes (CSS custom properties, self-hosted fonts), packaged as `packages/ui`.
- **Why:** the prototypes were axe-checked in three directions and both themes and carry the product's identity; rewriting them in Tailwind would lose that verification.
- **Alternative:** Tailwind plus Radix (ARCHITECTURE.md). Radix primitives are still used for behaviour where the prototypes had none (dialogs, popovers).

## D8. LLM provider (2026-10-23)
- **Decision:** a provider adapter with structured outputs. The first provider is Anthropic (the Sonnet-class family that ran proof F). Without a configured key every LLM-backed feature falls back to deterministic templates, and the Ask agent says plainly that it is unavailable.
- **Why:** reading `~/.secrets/anthropic-promo.env` is not authorised by the goal; see HUMAN.md H1.

## D9. Operational decisions made while building the platform (2026-10-23)

- **Database and Redis hosts are `127.0.0.1`, not `localhost`.** On Windows with Docker Desktop, `localhost` resolves to IPv6 first and psycopg waited the full 8-second connect timeout on every connection (measured: 127.0.0.1 0.01 s, localhost 8.02 s).
- **Row-level security without FORCE.** The application role does not own the tables, so RLS binds it; the migration role owns the tables and bypasses RLS, which is what lets the `SECURITY DEFINER` functions work on any Postgres host without a BYPASSRLS role. The API checks at start-up that its role is not a superuser, BYPASSRLS or the table owner (`assert_rls_effective`) and refuses to run otherwise. Alternative considered: FORCE RLS plus a BYPASSRLS function owner; rejected because managed Postgres services often cannot grant BYPASSRLS.
- **Tenants are created only by `create_tenant()`.** A direct INSERT into `tenant` or `membership` is denied by policy, so a signed-in user cannot enrol themselves in an existing tenant. Membership writes require the caller to be an owner of the tenant in scope.
- **QR tokens are stored hashed (lookup) and AES-GCM encrypted (so an owner can reprint a poster).** Key derived from the application secret by HKDF. Alternative considered: hash only, which makes a lost poster unrecoverable and forces rotation. Rotation replaces both, so every printed copy of the old code stops working.
- **Minimum three picks per response by default (`min_picks`, owner-adjustable 1 to 10).** PRD M2 says "about 5 picks"; tribes need enough signal per person. Not yet tested against completion rates.
- **No Qloo images are shown on the customer survey (yet).** Loading Qloo's image URLs from a guest's phone would send the guest's address to a third-party host. PRD M3 lists images; this is an open item (BUILD_STATE) until an image route through our own server is checked against Qloo's terms.
- **Free-text district is restricted to a short place name** (no `@`, links or 5+ digit runs), so the field cannot carry an email address or street address.
- **Honeypot, too-fast and burst responses:** a filled honeypot returns a normal-looking success and stores nothing; a response faster than `min_completion_seconds` or beyond 40 per QR point per ten minutes is stored as `quarantined` and excluded from analysis (counted for the owner as "held for review").

## D10. The picker goes to REST first (2026-10-23)

The goal says to use the harness primarily. Measured through the whole application against the live API, 13 calls each way: a search through the harness took 3.2 to 3.6 s (12.4 s for the first), the same search through REST took 0.35 to 1.0 s, and a whole picker journey took 45 s against 12 s. The harness starts a Node process for every call. Type-ahead cannot wait 3.4 s per keystroke pause, so the Guard sends the `picker` purpose to REST first and keeps the harness as the automatic fallback (and as first choice for every other purpose). Configurable with `NIGIWAI_QLOO_REST_FIRST` (comma-separated purposes; empty restores harness-first everywhere). Alternative considered: a persistent harness process (`qloo api mcp`), rejected for now because it exposes only a subset of the insights parameters; worth revisiting for the agent purposes. Review in HUMAN H3.

## D11. Web app decisions (2026-10-23)

- **Direction A, "Riso Counter", is the shipped visual direction.** The design system's own recommendation (DESIGN.md 3.4); no user has compared the directions, so this is a design judgement, not a measured result. The CSS is copied verbatim from the design system by `tools/sync_design.py` (D7), so a fix there carries over; only Direction A's two font families ship.
- **Next.js 16 App Router, React 19, TypeScript 5.9.** TypeScript 7 (the native compiler) was available on npm and was not used: the framework's tooling is built against 5.x. The browser only talks to its own origin; `/api/v1/*` is rewritten to the API, so cookies are first-party and there is no CORS.
- **Owner pages are client components behind a session provider**, not server-rendered with forwarded cookies. The data is private, per-user and changes after every action; nothing there benefits from server rendering or caching.
- **The guest survey keeps a draft in `sessionStorage`** (picks and optional answers, this tab only, cleared on send) so an accidental reload does not lose the picks. The consent text says so.
- **The survey page has no "Taste Card" and promises none.** The prototype's consent screen offered one; it is a Phase 2 feature (M15) and copy must not promise what is not built.
- **A guest's receipt code is the only way to remove their answers**, entered on the survey page. It is shown once, stored only as a hash, and cannot be recovered.
- **`GET .../survey` returns 200 with `null` when the business has no survey yet**, instead of 404, so a first visit does not log a failed request in the browser console (the project's zero-console-errors rule).
- **Quarantine threshold 2 s (`min_completion_seconds`).** A first run at 4 s quarantined a scripted but realistic sitting that restored a saved draft and tapped Start, Continue, Send. A person with a restored draft needs about 2 s; a script is instant. Not tuned against real guests.
- **Container images:** the API image carries Node and the Qloo harness so the harness transport works in production; the web image is a Next.js standalone build. Compose runs migrations as the table owner and the API as the non-owner role.

## D12. Tribes, the card, lineups and proof (2026-10-24)

Sources studied: proof tests D and G (code and reports in the research folder), ARCHITECTURE section 5, PRD M4, M7, M13, M15, M24. Licences: the HetRec data is research-only and never copied; scikit-learn, SciPy and NumPy are BSD; MusicBrainz data is CC0.

- **Tribes: ported from proof D and G, then tightened.** The matrix (each pick adds mass 1 over its Qloo tags, IDF over distinct picked items, rows length-normalised), soft NMF with `nndsvda` and `random_state=0`, K = 3 and the unlock bars (60 and 200) are as measured. **Reproduced**: with proof D's own preprocessing feeding the production stability code, soft-NMF K = 3 on the HetRec data gave raw stability 0.506 / 0.560 / 0.588 / 0.624 at N = 30 / 60 / 100 / 200 (proof D: 0.506 / 0.561 / 0.586 / 0.623), the permuted null 0.230 / 0.270 / 0.341 / 0.437 (0.226 / 0.274 / 0.342 / 0.436) and the random-pick null 0.271 / 0.344 / 0.441 / 0.582 (0.273 / 0.345 / 0.439 / 0.580): all twelve cells within 0.004, 30 crowds and 200 bootstraps each (`evals/tribes_hetrec_reproduction.py`, run 2026-10-24).
- **Where it beats the source.** Proof D judged stability against nulls by eye ("above the null"). The measured nulls are close to the real value at N = 200 (random picks 0.580 against 0.623), so a single comparison is not a safe test. Production runs a permutation test: the crowd must be more stable than all 19 draws of each null (one-sided p = 0.05), and shows no groups otherwise. On a planted crowd with no taste structure it refused groups in 5 of 6 trials.
- **Naming from genre tags first.** A first live profile of a real venue put audience and mood tags ("Passionate", "Loyal") on top because they fit everyone; names and the "what the room books" list now prefer genre tags and show the feel tags separately.
- **Fit order is canonical.** NMF is not convex, so row order can change the optimum; the pipeline sorts respondents by id before fitting, and the input hash covers picks, their tags, times and settings.
- **Tribe results are stored whole** (`tribe_version.result` JSON) instead of the `tribe` table in ARCHITECTURE section 6: one immutable document per version is what the proof panel and the card read, and nothing queries inside it.
- **A job queue in Postgres** (`job`, `SKIP LOCKED`, one pending job per kind and business) instead of procrastinate: no new dependency, the enqueue is in the same transaction as the response, and the whole thing is 150 lines with tests for retry, stale reclaim and two workers.
- **The Taste Card is authorised by the receipt.** The receipt is already the guest's deletion credential, so it needs no new secret; a definer function returns only that guest's picks plus the venue's name and place. The simple card makes no Qloo call; the fill-in is at most three, skipped when Qloo is slow, and a seed Qloo dropped (it answers with popular items anyway) makes that section unavailable instead of being shown as "because of your picks".
- **Places near here depend on what the venue is** (a bar's guests are offered bars). Without a category Qloo returned landmarks for a central London point.
- **Public lineups accept only exact matches** (same MusicBrainz id, or the same name after normalisation). Live on Mercury Lounge (33 events, 120 acts): 43 of the first 60 searched matched (72%), 43 of 120 overall because of the 60-call cap; proof O measured 69% for this venue. A venue with fewer than 10 events or 15 matched acts says "not enough public data yet"; groups need 60 events with two or more matched acts.
- **The proof panel never lists guest-made calls.** Picker and card calls carry what guests typed and picked, so they are counted by purpose and never shown row by row.
- **Qloo calls for the picker, the lineup job and tag backfill go to REST first** (extends D10): the lineup job took 211 s on the harness and 27 s on REST.

## D13. Audience reading for each group, M7 (2026-10-24)

Sources: research folder proofs K and L (Qloo `urn:demographics`; PRD section 5 and ARCHITECTURE `audience_context`). No code adopted.

- **What is built.** One demographics call per shown group, using the group's most-picked items (at most eight) as signals. Qloo returns one item per signal with age bands and a gender split relative to its average audience; the answers are averaged, weighted by how strongly the group picks each item. Two coarse readings result: age (younger-leaning, mixed, older-leaning) and gender (leans women, no clear lean, leans men). The reading is stored beside the groups in the tribe version, not inside them, because a stored group is rebuilt as a `TribeCard` for name carry-over.
- **Why these definitions.** Age is the contrast (45 to 54 and 55+) minus (under 25 and 25 to 29), the measure fixed in advance for proof L; the other age index in proof K failed its rule. The boundary is the midpoint of the young and older means in proof L (-0.45), with a band of 0.3 either side called "mixed ages". The gender cut-off of 0.15 is a choice (tested items ran 0.09 to 0.80). At least three items must have audience data, the smallest crowd the age contrast was checked on.
- **Evidence and its limits.** Gender direction matched common knowledge for 27 of 27 items (proofs K and L); the age contrast separated younger from older items at AUC 0.96 to 0.97 and told 3-item crowds apart 400 of 400 times, drawn from only 35 and 10 distinct triples. Ground truth was common knowledge, not a survey. Accuracy is **NOT VERIFIED**; the card says so and the label is "Modelled".
- **What it is not.** Guests are never asked their age or gender, and nothing about a person is stored. The reading describes Qloo's audience for the items, not the venue's guests.
- **Failure.** A failed or empty answer leaves that group "unavailable" or "thin" with the reason on the card; the groups themselves are never held back. Results are cached for 14 days by the Guard, so a refit with the same items makes no new call.

## D14. Soundcheck and the Fit Verdict (2026-10-24)

Sources: PRD M19, M9, M24; ARCHITECTURE 5.3, 14.1 and 14.2; research proofs L (test 3) and N. No code adopted.

- **A pure Fit package.** `packages/fit` takes groups, the answers Qloo gave for them and the owner's constraints, and returns the verdict. No network and no database, so the score can be recomputed by anyone from the stored inputs. The same inputs give the same score, band and fingerprint (the band's resampling is seeded from the fingerprint). Names and labels are not part of the fingerprint; ids, shares, answers, constraints and weights are.
- **One Qloo call per group, for any number of acts.** Live check (2026-10-24): an act's affinity is the same whether it is asked alone or in a batch with 20 reference acts and other candidates (identical to four decimals), and Qloo accepted 25 ids in `filter.results.entities` and returned all of them. So a Soundcheck costs one call per group and a whole suggestion run costs two calls per group (neighbours, then scoring). Group fit is the act's percentile rank among the references Qloo returned in the same call, because raw affinities are not comparable across signal sets (ARCHITECTURE 5.3).
- **Seeds are artists.** A group's seeds are its most-picked artists, weighted by membership, with at least two guests behind each; cross-category seeds did badly in proof I. A group with fewer than three eligible seed artists is left out of the score and the verdict says so. An act the group already favours is measured against that group's other favourites (Qloo does not score a signal), and the verdict says that too.
- **Lineup crowds have scenes, not tribes.** The guest model needs people; a lineup has events and acts. `scene_groups` groups the acts Qloo matched by their tags (same matrix and weighting as guests, rows weighted by nights played), at most three scenes of at least three acts each, always provisional. Fit needs at least 10 events and 20 matched acts (PRD M19), a higher bar than the lineup view itself (15 acts).
- **Constraints.** Only excluded genres can be tested against an act. Capacity and curfew are shown and plainly marked "not scored": Qloo has no stage-size, draw or set-length data for acts. A failed constraint stops the check before any Qloo call.
- **Peer evidence is omitted**, as the PRD allows: there is no data on what similar venues nearby book. Its weight moves to the group fit and the verdict says so; the weights (0.8 and 0.2, risk 0.5) are the v0 design, stored in `fit_weights`, and NOT VERIFIED.
- **Suggestions.** Qloo's neighbours of each group's seeds (never acts already played here or already among a group's favourites), scored exactly like a Soundcheck; the top three, and a Wildcard: below the median popularity of what was considered and ranked 0.6 or higher for each of the two biggest scored groups. The rule is deterministic; with no act that qualifies there is no Wildcard and the page says so.
- **Live result (real Qloo, three crowds of well-known artists, six acts with common-knowledge audiences):** each act fit its own crowd's group best, 6 of 6 (after the favourite-act fix above; the first run put Megadeth, one of the metal crowd's own seeds, in no group). Ground truth is common knowledge, not a survey, and the references are the other crowds' favourites, so a pass shows direction and not calibration. Suggestions on the same crowd put pop acts that fit all three groups on top (Ariana Grande 84, Harry Styles 81, Troye Sivan 71), and no Wildcard qualified: broadly popular acts score high everywhere, which the verdict's "what would change it" line makes visible.
- **A finding about My people, not fixed here.** On a clean synthetic crowd of 75 guests picking real artists from three genres, the tribes engine certified groups in about two runs in three and said "unstable" in the rest (p = 0.10 against 0.05: one of 19 permuted draws beat the real crowd). The decision is borderline at 75 guests and the bar is conservative by design (D12); the browser tests plant 120 so they do not depend on it. It is recorded as an open weakness rather than loosened without evidence.

## D15. Qloo against an AI alone, M23 (2026-10-24)

Sources: PRD M23, ARCHITECTURE 14.3; the Anthropic Python SDK documentation (context7, 2026-10-24).

- **The question and the two answers.** "Which acts are closest to this act?" put to Qloo (the act's neighbours in its graph, six real entities) and to a model with no tools and an instruction to say so when it does not recognise the act. Each act the model names is looked up in Qloo by exact name (case, accents and punctuation ignored, never a near miss) and marked found or not found. Agreement is counted, never ranked: the summary says "Neither list is ranked above the other", and a model that does not know the act is reported as exactly that.
- **What the model is sent.** Only the act's public name, cleaned to one line of at most 100 characters; no tools, nothing about a venue, an account or a guest (a test asserts the request body holds none of them). The reply is parsed as JSON of names only and each name is cleaned again, so text in a name can neither steer the model nor reach anything but a search box.
- **Cost control.** The model's answer is cached for everyone by question (model, normalised name), a daily cap per account (default 100) makes further questions say "the daily limit for AI answers has been reached", and the comparison for a stored Soundcheck is stored once.
- **Failure.** No key, a refused key, a busy or slow service, an unreadable answer: each gives a plain reason in the panel and leaves Qloo's side and the rest of the page working. The key is read from a file on the server (`NIGIWAI_ANTHROPIC_KEY_FILE`), never logged and never sent to a browser.
- **NOT VERIFIED: the model side against a real model.** The adapter is built on the official SDK and tested against an in-process stand-in for the API (answers, errors, junk, and the request it sends). No Anthropic key is authorised for this project (HUMAN H1), so no real model has answered. On a server without a key the panel says "no AI answer to compare: no AI service is configured on this server" and shows Qloo's neighbours. Until a key is authorised, the claim that Qloo beats an AI alone on small acts is not demonstrated by this product.
- **SDK note.** anthropic 2.3 carries its own copy of httpx (`httpx2`), so tests inject an `httpx2` mock transport; the SDK sends an API key as a bearer header.

## D16. Booking Brief, M22 (2026-10-24)

- **One document, three renderings.** The brief is a JSON document built from what is already stored (groups, suggestions, Soundchecks): no Qloo call, so it cannot disagree with the screens. The page, the share link and the PDF are all drawn from it. ARCHITECTURE 14.4 proposed printing the React page to PDF with a headless browser; that adds a browser to the API image and a worker that must start Chromium. The PDF is drawn directly with ReportLab (already a dependency) in the poster's embedded fonts, and a test extracts the PDF text and checks every act name, score, range and group against the document.
- **Names and scores only.** The document holds item names, our own scores and group labels; no entity ids, popularity or Qloo fields (a test asserts none appear in a shared copy). Qloo's terms on publishing even that in a link are **NOT VERIFIED** (H8), so a link is an explicit owner action, expires in 30 days, can be turned off, and its footer says "Taste data from Qloo".
- **Share links are snapshots:** the document as it was when shared, behind a 192-bit token stored as a hash and resolved by a definer function, so a reader needs no account and nothing else is reachable. An unknown, an expired and a turned-off link give the same answer.
- **A name the fonts cannot draw** is replaced with a question mark in the PDF and the footer says so; the page and the link show the real name.
- **Not built yet:** "venues nearby" (the PRD lists it) waits for the Grow module; the Today board feeds the brief from Phase 4.

## D17. Crowd map, M6 (2026-10-24)

Sources: PRD M6, design/map.html, the maplibre-gl-js documentation (context7), the OpenFreeMap terms of service (read 2026-10-24), the Nominatim usage policy.

- **MapLibre GL JS with OpenFreeMap tiles.** Free vector tiles from OpenStreetMap data with no account or key; their terms allow integration in a website and forbid scraping. The owner's browser fetches the tiles, so its address and viewed area reach OpenFreeMap (and its CDN); nothing about guests does. The style is Positron in light mode and Fiord in dark mode. If the style cannot be fetched the layers are drawn on a plain background and the page says the base map is missing; if WebGL is unavailable the list view takes over. Alternatives considered: Leaflet with OSM raster tiles (OSM's tile policy forbids a production app using its volunteer servers, and OpenFreeMap serves vector only), a pay-per-use tile provider (needs an account and money), no base map (the design's "God's Eye" feel is the streets).
- **The privacy rule is enforced on the server.** A site or neighbourhood with fewer than ten guests is sent as a pin or a count with no figures; a group slice under ten guests at a site is folded into "Other"; QR points under ten scans are not listed. Nothing in the browser can show what was not sent (tests check the JSON, not the screen).
- **Hexagons are H3 cells at resolution 8** (about 460 m along an edge), neighbourhood scale, from the Apache-2.0 `h3` library.
- **Districts are placed with Nominatim,** only for a district named by at least ten guests, bounded to about 35 km around the venue, at most three new lookups per request, one request a second with an identifying User-Agent, every answer cached for 90 days, and a failed lookup cached nowhere so it is retried. A place Nominatim does not know near the venue is counted and never guessed at. The browser tests run against a local stand-in so no test sends a question to the public service.
- **"Around you" is a separate request.** It is the one part that waits on Qloo (a harness call can take seconds), and a first version that bundled it left the page blank for ten seconds. The map shows at once and the places arrive after.
- **The view is saved in the address** (period, layers, selection, list or map), so "Copy view link" reopens it as it was. These links need an account: they are not public.
- **Layers built:** Your sites, Groups, Catchment and Around you, with a period control and a timeline. Gaps, Moves and Density wait for the Grow and Moves modules, and for a test showing that raw heatmap affinity is more than popularity (PRD M6 says it must be labelled demand context only).
- **MapLibre's worker** must be told where it is under Next.js (their documented `setWorkerUrl` pattern). Without it every source, GeoJSON included, fails with a single console error and nothing draws.

## D18. Judge mode, M25 (2026-10-24)

Sources: PRD M25, design/judge.html, the Devpost submission guidance in the Qloo kit, MusicBrainz and the Qloo Guard's monthly shares.

- **The demo venues are ordinary venues, not a separate code path.** Each is a business under one fixed system tenant (`6e1c0de0-0000-4000-8000-00000000d3a0`, created by migration 0009, no users and no memberships, so nobody can sign in to it). The same Soundcheck, suggestion, brief and map code builds and serves them, so what a visitor sees is what an owner gets. The public routes mirror the owner's under `/v1/public/demo/{slug}`, which lets the same three page components serve both.
- **A demo row can only point at the demo tenant.** `demo_venue.tenant_id` has a CHECK that it equals the system tenant, so even a bad write cannot list a real customer's venue to anonymous visitors (a test inserts one and expects the database to refuse). The public routes resolve a venue from that table only; neither id of the underlying venue is ever sent (a test searches every response).
- **Built ahead, served from storage.** `python -m nigiwai_api.demo` finds the place in MusicBrainz (exact name, the city in the area or the address, a valid position: the real record for Mercury Lounge names the area "Lower East Side", and the Austin namesake has a longitude of -457), builds the lineup profile, suggestions and comparisons, and warms the map's "around" layer. Opening a venue reads stored results and makes no Qloo call. Built live on 2026-10-24: Mercury Lounge 33 events and 89 of 120 performers matched, Empty Bottle 30 events and 31 of 71, The Hideout 11 events and 37 of 53 (the minimum is 10, so its scores rest on little).
- **A failed rebuild changes nothing a visitor sees.** The lineup and suggestion jobs clear their stored result when they fail, so a rebuild snapshots both first and puts them back on failure; the venue stays ready, the error is kept on its row for the operator, and the next look is hours away. A venue that never became ready is hidden and answers 503.
- **Old checks are dropped, suggested ones never.** Visitors' own checks and superseded builds are deleted after seven days, except any check the current suggestions point at (a stored check is reused when its inputs are unchanged, so a suggested act's check can be older than the window; the first version deleted them, and a test caught it).
- **Visitors can check any act, within caps.** A new check calls Qloo, so there is a per-network allowance (8 per ten minutes) and a site-wide daily cap (60 checks, 300 searches, 100 comparisons by default, in settings). The Guard's monthly share for the fit class is 5,000 calls, about 1,250 new checks, so the defaults leave room. Reopening a stored check costs nothing. Qloo's descriptive fields (`description`, `popularity`) are not sent for an act's verdict; search results carry Qloo's short description as the survey picker does.
- **Rebuilds are weekly, retried every six hours when due.** The worker looks for ready venues older than a week; each rebuild takes minutes, so they run one at a time on the worker. Rebuilding twice gave different top-three acts for Mercury Lounge (Dark Mean, All The Damn Kids, Alec Ounsworth, then Alec Ounsworth, Porlolo, Hot Panda) from the same 89 matched acts. The cause is **NOT VERIFIED** (Qloo answers can change between calls, or the seeds for a scene depend on the order acts resolved in); the page shows when a venue was last rebuilt.
- **Not built:** a "search any venue" box (the prototype has one; the owner's public-lineup start does it after sign-up, and a live version for strangers would spend hundreds of Qloo calls a go).

## D19. The Today board, M5 (2026-10-24)

Sources: PRD M5, design/today.html, ARCHITECTURE 5.3.

- **Computed from what is stored, every time.** Scans, opening hours, the crowd's groups, the suggested acts and their Soundchecks go in; the board comes out. Opening it makes no Qloo call (a test counts them), so it is fast and cannot disagree with the screens it summarises. Only the owner's decision is kept: accepted or dismissed per action per ISO week, so a new week starts undecided. An accepted action can be logged as a move (a `move` table that M11 will build on).
- **Opening hours are asked for** (Your venue, seven days, Monday first, a closing time earlier than the opening time means after midnight, with the small hours counted on the next day). Without them a quiet hour cannot be told from a closed one, so nothing is called quiet and the board says why.
- **A quiet stretch has to be clearly quiet.** The quietest three-hour stretch of each day, kept only if it has under half the scans of an average stretch, and only from 20 scans: with fewer it says "early look". The hours picture itself starts at 10 scans. These thresholds are choices, not measurements (NOT VERIFIED against real venues).
- **At most two actions plus a "needs more data" card.** Fill an empty chair (the quietest stretch and the best-scoring suggested act) and Book an act (the busiest stretch, else the owner's show night, else the day the room's public lineups skew to; a different act). Each line of evidence carries its label; the Soundcheck behind the score opens from the card. The nearby-partner line of the PRD and the draft card wait for Grow (M8) and Autopilot (M17).
- **Hold card.** The stretch with the most scans under 10 is offered as "what do these guests pick?", with how many more scans it needs, because a group under 10 is never described.

## D20. Ask Nigiwai, M12 (2026-10-24)

Sources: PRD M12, ARCHITECTURE 4 (the agent loop), the Anthropic Python SDK tool-use types (checked against the installed 2.3).

- **Fixed tools only.** `resolve_entity`, `related`, `places_nearby`, `verify_place`, `fit_verdict` through the Guard, and in crowd mode `my_groups`, `my_hours`, `my_moves` from the owner's own data. Culture mode has no owner tools, and a tool the mode does not allow is refused even if the model asks. A seed must be an id an earlier tool returned (the model cannot send Qloo an id it made up), places come only from the venue's own area, and a model gets 10 Qloo calls per question (a Soundcheck costs 4).
- **The model's answer is checked, not trusted.** The answer tool's items are kept only if a tool returned that id during this question, in order, once, with the name from Qloo's record. Where an item first appeared (surfaced by Qloo, or proposed by the model and confirmed by a lookup) is read from the trace. Free text is scanned for name-like phrases (two or more capitalised words, or quoted); one that no tool returned and that is not the venue is replaced by "[a name Qloo did not return]" and counted in a note. This is a heuristic: a lower-case name, or a name the model writes in an unusual way, can pass. An evidence label "measured" needs the owner's data to have been read and "observed" needs a Qloo call, else it becomes "modelled".
- **Failure is a plain list.** One reminder if the model forgets the answer tool; then, or on a model outage, a timeout (70 s) or too many turns (12), the owner gets what Qloo returned, unranked, with the reason. Nothing is retracted after it is shown: the answer is validated before it is sent.
- **Stored, with its trace.** Each answer is kept with the Qloo traces behind it (a Soundcheck's calls included), the model, token counts and the hash of the instructions it was given (`ask-v1`). Questions are limited to 40 a day per account, 10 in ten minutes per person.
- **NOT VERIFIED: any of this against a real model.** The loop, the tools, the checks and the page are tested with an in-process stand-in that plays scripted turns against a scripted or real Qloo. No Anthropic key is authorised (HUMAN H1), so how a real model behaves with the prompt, whether it respects the budget, and how often the name heuristic fires wrongly are unmeasured. The acceptance bar in the PRD (zero invented items across an answer set, every weak-coverage case carrying its warning) is met by construction for the item list and by the checks for the text, but has not been run over a real answer set.
- **Not built:** the AI-alone comparison inside Ask (the Soundcheck panel has one), streaming of the answer text itself (steps stream; the answer arrives whole after validation), and the closure checks beyond Qloo's own flag.

## D21. Onboarding, M1 (2026-10-24)

Sources: PRD M1 and Journey A, ARCHITECTURE section 6 (the profile and plan tables), the Anthropic tool-use types.

- **Two modes, one state machine.** The fixed form always works; the model-led mode only chooses which field to ask next and records what the owner wrote. A model that is missing, over its daily allowance (80 steps per account), slower than 45 seconds or down hands the interview to the form from where it was, with a notice. One turn with no usable tool call does not end the model's part; the next fixed question is asked and the assistant carries on.
- **The code decides what is true.** Every value, typed, clicked or recorded by the model, passes the same validator (`onboarding_model.normalise`): kinds of business and goals from fixed lists, a currency from the ISO 4217 list, hours as seven days, and so on. The model's `record_answer` also needs a quote that really is in what the owner wrote (case and spacing ignored), so it cannot fill a field from the business name or from its own idea of the type. The model cannot ask about a field outside the checklist, cannot ask more than eight questions in all, and cannot write anything the owner sees except the question text; its own prose is never shown.
- **Eight questions, with the four required ones protected.** Type, address, goals and currency come first; an optional question is allowed only while the required ones still fit within eight. Capacity is the one that usually falls off the end; the owner can add it, or any answer, from the check without it counting as a question.
- **Nothing is written until the owner confirms.** The interview is stored on its own (`onboarding_session`); the business and place are created or updated only on confirm, together with a new `business_profile` and `dashboard_plan` version in one transaction. An empty answer means "not given", never "delete": hours, show nights, excluded genres and capacity already on record are kept unless the owner gives a new value. A second interview starts from what is on record and asks only what is missing.
- **The plan is code, not a model's layout.** `plan_for(profile)` is a small set of rules, each with a reason shown to the owner ("On because you host live music"). Core tools (Today, Your venue, Survey, My people, Ask, QR posters, Proof) are always on; the Crowd map is on; Soundcheck and the Booking Brief follow whether the venue books live acts or the owner wants to book better acts. The owner can switch any non-core, built tool, each switch a new plan version, and the menu hides tools the plan leaves off (their pages still open by address). Tools not built yet (Grow, Sound plan, Moves) are listed as "Not built yet" and cannot be switched on. The PRD's "an AI chooses the dashboard shape" is therefore deliberately not done: a fixed rule set is explainable, testable and cannot invent a module.
- **Address search is the owner's press of a button.** "Find it on the map" sends only the typed address to OpenStreetMap's Nominatim (cached 90 days, one request a second, the contact in the User-Agent, nothing as you type), and the owner picks a match or goes on without a position. Impossible positions (a longitude of -457 appeared in real data) are dropped. The time zone is the browser's, shown and editable on the check, because a wrong one silently shifts every scan's hour.
- **Shared opening-hours editor.** The editor now used by Your venue and by onboarding is one component. It also gave the venue page the styling the editor had been missing since opening hours were added: `.hours-edit` had no CSS, found while looking at the new screens.
- **NOT VERIFIED: any of the assistant mode against a real model** (HUMAN H1). The tools, the checks and the fallbacks are tested with an in-process stand-in that plays scripted turns and with a small HTTP stand-in in the browser tests. How a real model uses the prompt (how often it asks fewer questions than the form, how often a quote is refused) is unmeasured. The eight-question limit, the checks and the fallbacks do not depend on it.
- **NOT VERIFIED: the persona result.** The five personas (cafe, bar, hotel bar, boutique, venue) are invented by us, one fixed form answered the way each would; they show the rules ask at most eight questions and enable the modules the rules say. They are not evidence about real owners.
- **Not built:** "speaks in the owner's language" beyond currency (English only; the profile carries `language: en`), choosing the exact map position by dragging a pin, and a price level question.

## D22. The Sound plan, M26 (2026-10-24)

Sources: PRD M26 and M19, the Fit package (`raw_score`), `services/hours.py`.

- **No new Qloo call.** The suggestion run already scores about 30 acts against each group of the crowd (one call per group). It now keeps a compact record of every act it scored (the act, our score and the rank it earned for each group, never Qloo's own response) beside the three suggestions and the wildcard. The Sound plan is computed from that record, the groups' stored weekday and hour rhythm, and the opening hours. Opening the page costs nothing and cannot disagree with Soundcheck: it uses the same formula, so an act scored for a stretch that is entirely one group gets that group's own score.
- **A stretch is a part of the day on weekdays (Monday to Thursday) or on the weekend (Friday to Sunday).** Four parts: morning (05:00), afternoon (12:00), evening (17:00), late night (22:00 to 05:00). Each stretch's mix of groups is the share of that stretch's scans that fell to each group (soft membership, measured). Opening hours remove a stretch the room is never open in; a stretch with fewer than 20 scans, or whose groups Qloo could not rank the act for (under 60% of the stretch), is shown as thin and names no act. These thresholds are choices, not measurements.
- **Busyness is scans per open hour compared with the busiest stretch** (busy from 75%, quiet under 35%): measured, relative, not a headcount. The plan makes no claim about mood, spending or what a person would like to hear, because there is no evidence for a mapping from a crowd to a tone (PRD M26 cites one 2003 restaurant study only). The venue type is used only through opening hours; nothing maps type to genre.
- **A venue known only from public lineups** gets one list for the whole week with a note that lineups say who played, not when guests come. Time of day needs the owner's own scans.
- **Stale guard.** The record is tied to the version of the crowd it was scored for. If the groups are refitted the page says the acts are out of date and offers to score them again; a suggestion run saved before the record existed says the same.
- **On by default for every kind of business except a promoter or a festival.** The plan lists it with that reason, and the owner can switch it.
- **NOT VERIFIED: that the ranking is good.** No outside-source relevance check of Sound plan quality has been run, and the weights are the uncalibrated Fit weights (`v0`). It does not play or license any music.
- **Not built:** a public demo tab for the Sound plan (the stored demo suggestions predate the record and are rebuilt weekly), per-day plans, and an export to a music service.

## D23. Moves and results, M11 and the honest part of M20 (2026-10-24)

Sources: PRD M11 and M20, Journey C step 3, and the `move` table from the Today board (D19).

- **A move is what changed, with the slot it was aimed at.** Kind (act, event, menu, ad, price, other), a title, the day it started and optionally ended, the days of the week and hours it was aimed at (none means all), and a note. A move logged from an accepted Today action carries that action's slot (the quiet Wednesday afternoon, the busy Friday evening), so the owner does not retype it. The Moves page lists them with their results; the Today card links to it.
- **The comparison is the same slot in the four weeks before and the days since.** Scans (guests who chose to answer, never a headcount) falling on the move's days and hours, counted per day the slot occurred and only on days the venue is open. The rate after over the rate before comes with a 90% interval from the exact conditional method: given the total number of scans, the share that fell after is binomial, so the interval is a Clopper-Pearson interval turned into a rate ratio, and the p-value is the matching exact test. The verdict is "more" only if the whole interval is above 1, "fewer" only if it is all below 1, and "inconclusive" otherwise.
- **It refuses to say before there is anything to say.** Fewer than two matching days since the start, or fewer than eight scans in the slot across both periods, is "too early", with the reason in words. The days after can never outnumber the days before, so a move with enough days after always has something to compare with.
- **It never says the change caused anything.** A season, the weather, a neighbour's event or a holiday moves scans too, and one before and after has no control group. The wording on every result says so, and the ledger counts inconclusive and too-early moves as answers, not failures.
- **The mix of groups before and after is shown** for the same slot when there are fitted groups and at least 10 scans in the period, as shares measured from guests' scans; under 10 it says so and shows nothing. A different mix is not presented as an effect.
- **Deviation from the PRD, on purpose:** M20 says the outcome ledger adjusts Fit Verdict weights per business. It does not. A handful of weeks of scans at a few venues cannot support re-weighting a score, and an automatic adjustment from tiny samples would be the kind of confident claim the product is built not to make. The ledger only reports what has been tried and how it came out. Per-business weights stay `v0` and uncalibrated.
- **Not built:** sales or till data (PRD M11 P2), a control venue or matched weeks from last year, experiments that assign a move to some weeks and not others (M20's "run as a simple experiment"), and a move that spans midnight (use two slots).

## D24. Drafts: Autopilot's approval gate and the ad hand-off, M17 and M10 (2026-10-24)

Sources: PRD M17 and M10, Journey C step 4 and Journey E.

- **Text the owner reads, changes and approves; the product sends nothing.** Four kinds: an enquiry to the act, an event page, a post, and an ad angle for one group. They are made from stored facts only: the venue's name, address and capacity, the act and the slot of an accepted Today action, the group an act fits best and the names of items that group's members picked, and the survey reward if the owner set one. A fact the product cannot know (the booker's name, the date, a fee, doors time, ticket link, the call to action) is left as a [bracketed] gap, and **a draft with a gap left cannot be approved**. Approval marks the saved words as the owner's own and records who and when. For an enquiry it then offers "Open in my email", a `mailto:` link with the draft and no address, so the owner's own mail program sends it, if they choose.
- **Approval belongs to the exact words.** Editing an approved draft returns it to draft; the page will not approve unsaved changes; a withdrawn draft cannot be edited. Create, edit, approve, withdraw and delete are each written to the audit log (what, who, when).
- **Drafts need a reason to exist.** Enquiry, event page and post come only from an action the owner accepted on Today; an ad angle only from a group that has picks to write from. A request naming neither, both, or something the board does not hold is refused.
- **The ad angle names no audience.** It says what the group picks most, a headline within 40 characters and primary text within 125 (the usual short-feed limits, checked in code), and leaves the channel and call to action open. It does not say who the people are, and no Qloo audience data is exported as a segment.
- **Templates, not a model.** No AI service is authorised (HUMAN H1), so the wording is fixed text with facts filled in. That is plainer than a model's draft and will read stiffly; it is also never wrong about a fact, which a model's draft could be. A model could polish the text later behind the same gap and approval rules.
- **Not built:** sending (email, calendar, ad platforms), contact details for acts (the owner supplies them), menu-board text and a poster draft (PRD M17), channel connectors and ad-library lookups (M10), results flowing back per group into the tribe model, and the AdCP standard.


## D25. Grow, M8 (2026-10-24)

Sources: PRD M8 (P1) and §15 Phase 4, ARCHITECTURE §4.5 (closure check) and §12 Phase 5, proofs H to J (`../qloo/test-results`), and a probe of three real venues described below.

- **This reverses an earlier call.** BUILD_STATE first recorded Grow as "not built, on purpose" because its place and cross-category parts lean on exactly what proofs H, I and J did not establish. That was the wrong answer to a real gap: PRD Phase 4 lists Grow, and a feature can be built so that it states what its own evidence allows instead of being left out. Grow is built that way: every part is labelled, and what it may claim is decided by checks the run makes on the owner's own groups.
- **What a run does.** One button press queues a worker job (about a dozen to twenty-five Qloo calls, a per-user limit of six requests in ten minutes, one waiting job per venue). It reads the same groups Soundcheck uses (guests, or the scenes made from public lineups when there are none). For each group it asks Qloo for the neighbouring acts of the group's favourites (the same request Soundcheck's suggestions make, so a recent one is served from the private cache), then for places of the venue's kind inside the venue's radius and out to five times that (capped at 50 km), with the crowd's taste as the signal and without it. Every place is asked about once more for Qloo's closure flag, and a closed one is left off. Our own derived record goes in `grow_run` (names, ids, distances, counts and the numbers behind each check, never Qloo's answer); opening the page reads that row and makes no Qloo call (a test counts them). A run made for an older version of the groups is shown, marked, with a button to look again.
- **The probe.** Three real venues (Mercury Lounge, The Hideout, Empty Bottle), three groups each, real Qloo, asked for artist neighbours and for bars inside 800 m and out to 4 km with each group's favourites as the signal. Neighbouring acts overlapped 0.00 to 0.05 between groups: group-specific. Bar lists did not: the first ten overlapped 0.54 pairwise at Mercury Lounge and 1.00 at the other two (ring lists 0.33, 0.82 and 0.82), and with the crowd's taste against without it the overlap was 0.11 to 0.18, 1.00 and 0.67. Place affinities all sat between 0.85 and 0.94, so no threshold can be set on them. Reading: Qloo's artist graph tells groups apart and its bar lists mostly do not, which matches proofs H to J.
- **Three checks decide what is shown, each run, with the numbers printed.** (1) Ghost customers are shown only if the groups' neighbouring-act lists overlap by at most 0.5. (2) A place list is called "matched to your crowd" only if giving Qloo the crowd's taste changed at least half of its first ten places against the plain list; otherwise it is "near you" and says so. (3) Places are listed per group, and a group can be a gap candidate, only if the groups' lists overlap by at most 0.3 (two unrelated top-10 lists drawn from the same 20 places overlap about 0.33 by chance, so this means the groups were genuinely given different places). On all three real venues check 3 fails, so the real answer today is: ghosts per group, places for the crowd as a whole, no gap claimed. All three limits are choices, not calibrated, and are strict on purpose. A seeded answer that Qloo's guard flagged (a dropped seed, or every score equal) is treated as no answer.
- **Ghost customers** are genres that at least two of a group's neighbouring acts carry, that also carry a genre the group clearly has (at least a quarter of its members), that at most 5% of the crowd carries, and that are not a variant of a genre the group already has ("Metal" beside "Heavy Metal" was a first live result and is now excluded). A count of guests under 10 is never shown as a number, only "fewer than 10". For a venue known only from public lineups the unit is acts, and a scene of three acts is readable; the page says which. Genre means a tag in the genre or subgenre namespace; moods, themes, instruments and audience tags are ignored.
- **PRD M8's four parts, as built.** Ghost customers: built as above. Gaps: built, but only where check 3 passes (a group with no place of its own among Qloo's first ten), because "no matching place" needs a place list that depends on the group. Where else: the ring list, per group only where check 3 passes. Lookalike venues: the crowd-level ring list. All are labelled modelled when matched and observed when only near, and carry "ideas to check, not proof".
- **Existence.** ARCHITECTURE §4.5 allows an OpenStreetMap or registry check. None is added: it would be a new public service called per place. Places carry Qloo's flag only and say "not independently confirmed". The venue itself is left out by name and by being within 40 m of its own point.
- **Why the goal "Reach new kinds of customers" switches it on.** Grow costs Qloo calls and needs at least 60 guests (or lineups), so it is on only for owners who asked for it; its page opens for anyone by address.
- **Live check.** A London bar with three crowds of well-known artists (pop, crooners, metal), real Qloo, 12 calls. Groups got different neighbouring acts (0% in common). Ghosts: the first run gave four across the three groups; two were a variant of a genre the group already had (a genre listed beside its longer name, and a sub-style of pop beside pop), which is why variants are now excluded, and the second run gave one, for the crooners, a genre beside blues and jazz, with fewer than ten guests carrying it. Places: "matched to the crowd" (the crowd's taste changed 67% of the near list and 95% of the far list) but not told apart between groups (0.59 in common, against the 0.3 needed), so no per-group places and no gap. Names are not recorded here: they are Qloo's data.
- **NOT VERIFIED.** That a ghost genre is a real audience that would come, or like the acts shown; that the limits are right; that Qloo's place lists carry any group-specific signal at all (three venues, one city pair, one probe); that places Qloo lists as bars are bars (a cinema and a rooftop garden appeared once in a live list; the Guard's category filter did not remove them).
- **Not built:** competitor reviews or sentiment, ranking places by sales, any count of customers, and a per-group "where else" on data that failed check 3.
