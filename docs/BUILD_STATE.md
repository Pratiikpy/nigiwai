# Build state

Last updated: 2026-10-24 (Phases 4 to 6: Today, Ask, onboarding, Sound plan, Moves, Drafts). Read this first after any context reset.

## What this is
Nigiwai (賑わい): a crowd-reading tool for venues; hero flow Soundcheck. Specs live in the research folder `../qloo` (the research folder next to this repo) (PRD.md v0.6, ARCHITECTURE.md with section 14, design/, BUILD_BRIEF.md). This repo is the product. Rules: no push, no public deploy, no accounts, MIT, decisions in docs/DECISIONS.md, human questions in docs/HUMAN.md.

## Resume instructions
1. `cd` into this repository; `git log --oneline` shows verified phases.
2. Read this file, DECISIONS.md and HUMAN.md.
3. Local services: `just up` (Postgres+PostGIS and Redis in Docker; Docker Desktop must be running). Python: `uv sync`. Web: `pnpm install`.
4. Continue at "Current phase" below.

## Phase 2 evidence (2026-10-24)

- **Tribes engine reproduces the research.** With proof D's own preprocessing feeding the production stability code on the HetRec data, soft K = 3 gave raw stability 0.506 / 0.560 / 0.588 / 0.624 at N = 30 / 60 / 100 / 200 against proof D's 0.506 / 0.561 / 0.586 / 0.623 (`evals/tribes_hetrec_reproduction.py`; the data is research-only and is not in the repo). A planted crowd with no taste structure was refused groups in 5 of 6 trials.
- **Chain, end to end through the browser:** planted crowd of 25, 70 and 200 guests -> job queue -> worker -> `tribe_version` -> My people (empty, thin "25 of 60", provisional "Group A..." and named) -> guest Taste Card placement. Every state: axe clean, zero console errors, screenshots looked at (light, dark, phone, desktop).
- **Taste Card call budget (PRD exit check), live Qloo:** 200 synthetic scans, each a different random three real items sent through the real survey and card endpoints from its own address: mean 1.75 Qloo calls per card, maximum 3, 349 live calls in total, every fill-in `ok`. A first run failed at scan 21 because every scan shared one address and hit the 20-an-hour fill-in limit; the test now gives each scan its own address.
- **Public-lineup start, live:** Mercury Lounge, real MusicBrainz and real Qloo, 33 events and 120 acts, 43 of the first 60 searched matched exactly (72%); proof O measured 69% for this venue. Browser test passed.

The reference is common knowledge about the acts, the same weak ground truth as proofs K and L; accuracy is **NOT VERIFIED** and the card says so.
- **Proof panel:** invented items shown to the owner: 0 of N (every item must exist in what Qloo returned; a corrupted stored result is reported as invented in a test). Guest-made calls are counted by purpose and never listed.
- Bugs found by the Phase 2 tests and fixed: a refit with unchanged input stored a duplicate version; the related-tastes request put the signal in the exclusions; places near a central London point were landmarks until the category followed the business type; Qloo silently ignores a seed it does not know and answers with popular items, so a dropped seed now makes that card section unavailable; a stale cache survived test runs; a phone nav-drawer race in the browser tests.

## Phase 4 to 6 evidence (2026-10-24)
- **Final run (2026-10-24), on a fresh clone of commit 617fd11 with a fresh database, following the README.** `just setup`, `just up` and `just migrate` exit 0. `just test`: 148 unit tests and 12 web unit tests passed. `just test-integration` (API against real Postgres and Redis with a scripted Qloo, the database built from the 16 migrations): **475 passed** in 14.5 minutes. `just demo` built all three judge-mode venues from real MusicBrainz and real Qloo (about 6 minutes). Production web build, then **browser tests in real Chrome, phone and desktop: 87 passed, 11 skipped (the opt-in live specs), none failed** (16 minutes); the judge-mode spec opened a real demo venue with its suggested acts on screen in 243 to 296 ms (the PRD bar is 10 seconds). **Live against real Qloo through the browser: 10 passed** (guest picker and card, public lineups, group audiences, Soundcheck with suggestions and the Booking Brief, Grow) and **through the API: 20 passed** (`just test-live`). ruff, eslint, mypy --strict (97 source files) and tsc were clean at that commit. The test doubles (a scripted Qloo and a scripted model) are used only in the integration and browser suites; the live runs use the real Qloo API. The model-led features had not yet been run against a real model when this paragraph was written; see the next section.
- **Machine pressure, said plainly (again).** Two browser runs and one test run in this phase failed for reasons outside the product: Docker Desktop stopped (every browser test then fails in under a second), and at under 2 GB of free virtual memory argon2 and the Anthropic client's DLL fail to load. Each passed when the machine was healthy again; none was a code defect.
- **Today board (M5).** Computed from stored scans, opening hours, groups and suggested acts every time it opens, with no Qloo call (a test counts them); only the owner's accept or dismiss per week is stored. Quiet stretches need 20 scans, hours pictures 10. Browser tests cover a new venue, an early look, no opening hours, a full week, decisions that stay, and the link to Moves and Drafts.
- **Ask Nigiwai (M12).** A tool-using model whose items must have been returned by a Qloo call during the question, with names taken from Qloo's records. Tested with a scripted model against scripted and real Qloo: invented items refused, an invented name in the sentences removed, labels that were not earned downgraded, a model outage or timeout still giving a plain answer, the call budget held. Then run against a real model and real Qloo: 5 of 5 questions answered by the model in both modes after the changes in D27, and in a real browser.
- **Onboarding (M1).** A fixed form and a model-led mode share one state machine; every answer, typed or recorded by the model, passes the same validators, and the model's quote must be words the owner wrote. At most eight questions, with the four required ones protected (five invented owners: cafe, bar, hotel bar, boutique, music venue). The model cannot ask outside the checklist, cannot ask a ninth question, and its own prose is never shown. Nothing is saved until the owner confirms; profile and plan are versioned; an empty answer never erases what is on record. Failure of the model, its daily allowance (80 steps), or a 45 second limit hands over to the form. Address search is a button press that sends only the typed address to OpenStreetMap (cached 90 days). The model mode runs on a scripted model in the automated suites and on a real model in the live runs (D27).
- **Sound plan (M26).** Acts to play by time of the week from the groups' scan rhythm and the acts already scored (the suggestion run now keeps a compact record of every act it scored, never Qloo's own answer). Stretches under 20 scans, or when the venue is closed, name nothing. Opening the page makes no Qloo call. **Plan quality is not checked against an outside source and the weights are the uncalibrated `v0`.**
- **Grow (M8, D25).** Built after a probe of three real venues showed that Qloo's neighbouring acts differ between groups (overlap 0.00 to 0.05) but its bar lists mostly do not (0.54, 1.00 and 1.00). So a run prints three checks on the owner's own groups and the page claims only what they allow: ghost customers per group only if the groups' neighbouring acts differ; a place list is "matched to your crowd" only if giving Qloo the crowd's taste changed at least half of it; places per group, and a group with no place of its own as a gap candidate, only if the groups were given different places. On all three real venues the last check fails, so the page lists places for the crowd as a whole and claims no gap. Tested: 23 model tests, 21 integration tests with a scripted Qloo (ghosts, each place mode, closure and the venue itself left out, public-lineup basis, stale and failed runs, roles, a limit of six requests in ten minutes, one waiting job, a count of Qloo calls on page open), one live run through the API and worker against real Qloo (12 calls, all assertions on what a run must never do), and browser tests on phone and desktop for every state with axe, console and screenshots looked at in light and dark. **Not verified:** that a ghost genre is an audience that would come; that the limits (0.5, 0.5, 0.3, 5% and 25%) are right; that Qloo's place lists carry any group-specific signal at all.
- **City Taste Atlas (M16, D26).** The opt-in and the privacy machinery, built before there is any data to show: a venue joins with an explicit step and can leave; `atlas_rebuild()` pools the opted-in venues' own responses into `atlas_cell` inside the database (a venue counts with 10 answers, a cell opens with 5 such venues, an item is listed with 10 answers from at least 3 venues and no more than half from one); the table has no column naming a venue, tenant or location; column checks restate the minimums; the application role can read the table and run the function but never write it. Tests: database-level (every minimum, a venue under ten answers, quarantined answers, another cell, leaving and the audit log, a venue that has not joined sees nothing, the checks refuse a hand-written row, the column list, the role's rights, Python and SQL agreeing on the cell of 200 random points) and API-level (roles, another account, junk bodies), plus browser tests on phone and desktop of every state with five real venues planted in one square. **It shows no real data until neighbours join**, and Qloo's terms for item names in a shared view are not confirmed (H11).
- **Moves (M11, M20).** Same slot, four weeks before against the days since, per matching open day, with an exact 90% interval; "inconclusive" and "too early" are first-class answers and the page never claims a cause. The outcome ledger counts what was tried; it deliberately does not re-weight scores (D23).
- **Drafts (M17, M10).** Enquiry, event page, post and ad angle from stored facts; a draft with a [gap] cannot be approved; approval belongs to the saved words; every step is audited; nothing is sent.
- **Looked at.** Screenshots of the interview (question, places, hours, refused answer, check, saved, assistant, fallback), the plan page, Sound plan, Moves, Drafts in light and dark on desktop and phone profiles; axe clean and zero console errors in each state the specs reach.
- **Bugs found by these tests and fixed (not exhaustive):** the hours editor on Your venue had no styling at all (found while looking at the onboarding screens, now one shared component); the side menu marked "Soundcheck" and "Sound plan" both current because one name starts with the other; the conversation log was a scrollable region a keyboard could not reach; the interview's "what I understood" list was an invalid definition list; Moves and Drafts bodies failed on ISO dates under strict validation; the poster test's QR reader (OpenCV's older detector) missed about one A4 poster in eight while the code was fine (60 of 60 read with the newer detector), so the test now uses that; a stale form error stayed on screen after the field was fixed.

## Open items and limits
- **NOT VERIFIED: speed with real people.** The PRD target (a real phone, median 20 s, five phones) cannot be measured here. The scripted run completes in a few seconds, which says nothing about people. Copy says no time claim.
- **NOT VERIFIED: the 429 onset and concurrent scanners.** No load test against live Qloo has been run; the Guard keeps to 8 requests per second by design and the picker is capped at 20 live searches per sitting.
- **NOT VERIFIED: the CI workflow** (`.github/workflows/ci.yml`) has not run, because nothing is pushed.
- **Places are not pickable** (PRD M3 lists places). Place search needs a location-bounded design and the Guard's place rules; not built.
- **No Qloo images on the survey** (privacy, D9), although PRD M3 lists them.
- **Posters:** names or reward text outside Latin script are left off the printed page (the QR and URL still print) because the bundled fonts are Latin only. The survey and picker handle any script.
- **District is free text** limited to a short place name; a street name without digits would still pass. Replace with an owner-defined list if this proves a problem.
- Minimum three picks and the 2 s quarantine threshold are choices (D9, D11), untested against real guests.
- Reverse proxy must overwrite `X-Forwarded-For` (README), or rate limits can be dodged.
- Team invitations are built (D29: links, no email). There is no emailed password reset or email verification (no email service is authorised, HUMAN H2); a recovery code stands in (D30), so someone who loses the password and the code cannot get back in.
- `app_user` has no row-level security (D30): the privacy of a sign-in address rests on the API's queries. Move login lookup behind definer functions and enable RLS before a public launch.
- Starting a new venue from an existing login is not built: a second account is made by signing up with another address (or by being invited).
- Production Postgres: migrations as the table-owner role, the API as `nigiwai_app`.
- **NOT VERIFIED: tribe stability on real QR picks.** The thresholds (60 and 200) come from stability on public listening and Qloo-tag data (proofs D and G), not from guests answering a QR survey. Usefulness of the groups to owners is untested.
- **NOT VERIFIED: the age and gender reading is accurate.** Direction matched common knowledge in the research folder's tests and in the live run above; no survey ground truth exists. It is labelled Modelled, and a group with audience data for fewer than three of its top items gets a plain "not enough" note instead of a reading.
- **NOT VERIFIED: the rate limits** (20 card fill-ins an hour per address, and 40 responses per QR code in ten minutes before new ones are held for review) against a real busy venue; both are choices. One address behind a shared Wi-Fi counts as one.
- **Taste Card:** the richer version (P1) is not built; places as picks are not built (above).
- Lineup start covers music venues in MusicBrainz only; other venue types get "not enough public data yet". MusicBrainz asks for a contact: set `NIGIWAI_LINEUP_CONTACT` before public use (HUMAN H6).
- **NOT VERIFIED: a demo venue rebuilt twice gives the same suggestions.** Mercury Lounge's top three changed between two builds from the same 89 matched acts (D18).
- **NOT VERIFIED: the Fit score predicts anything about a crowd's enjoyment.** The weights are a starting design; there is no outcome data (`docs/SUBMISSION.md`, section 6).
- **"Search any venue" on the front door is not built** (the prototype has it); the owner's public-lineup start does the same after sign-up.
- **Not built:** M18 Don't-do list (experimental, to be released only after a held-out test; there is no data on what people dislike to test it against), sending anything from Drafts, ad-platform connectors, till or sales data, experiments that assign a move to some weeks only, automatic re-weighting of scores from outcomes, and a Sound plan tab on the public demo venues (their stored suggestions predate the record it needs and are rebuilt weekly). The CI workflow has still never run.
- **The model-led features have run on a real model, but not on Claude** (D27). Onboarding (five owners in their own words: 5 of 5 stayed in the assistant, 20 of 20 then 16 of 20 required facts from the first paragraph), Ask (5 of 5 questions answered by the model, in both modes, against real Qloo), the AI-alone panel (3 of 3 acts) and both flows in a real browser on phone and desktop. The model was NVIDIA's `nemotron-3.5-lightning-30b-a3b`, at Prateek's direction, because the Anthropic key needs a workspace id nobody has supplied (HUMAN H12). **NOT VERIFIED:** any of it on Claude; quality over more than a handful of owners and questions; the hosted service's rate limits at real traffic (a 429 hands the interview to the form, and Ask to its plain list, with the reason shown). A verdict's wording can carry colour no tool returned; only names, ids and numbers are checked.
- **NOT VERIFIED: Sound plan ranking quality** against an outside source; **Moves** reads scans only (no sales), so even a clear rise is not evidence of revenue.
- **Moves** loads all of a venue's scans in the comparison window on every request (fine for the pilot sizes tested; cache it before a venue has tens of thousands).
- **Address search** sends the owner's typed address to OpenStreetMap's public search (HUMAN H10).
